# 보석 왕국 — 규칙 명세

로얄매치 / 로얄킹덤 계열 3매치의 규칙 명세.
**컨셉은 보석이지만 엔진에 색은 인덱스일 뿐이라, 컨셉을 바꿔도 이 문서는 그대로다.**

## 이 문서의 사용법

이 문서가 **유일한 판단 기준**이다. "이게 재미있나?"(사람만 판정 가능)를
"레퍼런스와 같게 동작하나?"(기계가 판정 가능)로 바꾸는 것이 목적이다.

| 표시 | 뜻 |
|---|---|
| ✅ | 구현됨 + 테스트 있음 |
| 📖 | **출처로 확인됨** + 미구현 → 다음 할 일 |
| 🔶 | 출처를 못 찾음 → 직접 플레이해서 확인 필요 |
| ⬜ | 우리가 정할 것 (레퍼런스에 매이지 않는 부분) |

규칙을 바꾸려면 **`engine/specials.ts` 상단의 표만** 고친다. 로직은 표를 읽을 뿐이다.

## 조사 요약 (2026-08-25)

> **로얄킹덤의 코어 퍼즐은 로얄매치와 동일하다.** 아이템(브레이커)의 생성·발동

> 차이는 코어 밖에 있다 — 난이도 곡선, 골렘 같은 신규 장애물, 10레벨마다의
> 킹덤 레벨(PvE).

→ **코어 엔진은 로얄매치 규칙 하나만 정확히 구현하면 된다.** 로얄킹덤은

### 6.0 카탈로그 — `data/elements.ts`

레퍼런스 요소를 **축 조합의 표**로 미리 구성해 뒀다. 59종.

```
grass jelly marble mushroom                          하단 레이어
chain ice honey dark-honey cloud roof ...            상단 레이어
box crate log barrel safe steel vault bastion ...    막는 장애물
honey-pot flowerpot turtle snowman                   번지는 것
ghost/tombstone paint-bucket/color-mixer
  metal-tower/castle                                 앞을 치워야 열리는 것
magic-wall serpent-head/serpent-body                 여러 칸에 걸친 하나
electro-crate firework-tower                         부서지며 남기는 것
golem giant-golem giant-drill water-tower            자리를 옮기는 것
mailbox magic-hat jar cauldron scarecrow ...         생성
shelf cupboard potion-bottle bird-house ...          그릇
tube wall conveyor tesla laser fireworks             특수
```

**새 요소를 넣는 방법 = 이 표에 한 줄 추가.** 엔진도 표기법도 안 건드린다.
배치에서는 대괄호로 쓴다:

```
[box]        기본 겹
[box:4]      4겹
[shelf:R3]   빨강만 받는 3칸 선반
[chain]R     사슬에 묶인 빨강 보석
```

⚠️ **동작이 출처로 확인된 건 34종이다.** 나머지 26종은 분류에 맞춘 합리적
추정이고 `verified: false`로 표시돼 있다. `unverifiedElements()`가 그 목록을
돌려주므로, 레퍼런스를 플레이하며 하나씩 확정하면 된다 —
**"무엇을 확인해야 하는지"가 코드 안에 목록으로 있다는 게 요점이다.**

레벨 11이 카탈로그 전시장이고, 그와 별개로 **요소마다 전용 시험 레벨이 하나씩**
자동 생성된다(`data/testLevels.ts`). 표에 줄을 추가하면 시험 판도 저절로 하나
생긴다 — 손으로 적으면 새 요소를 넣을 때마다 빼먹게 되고, 빼먹은 건 영영
확인되지 않는다.

종류를 하나씩 나열하는 대신 **동작 축**으로 모델링한다.

| 축 | 뜻 | 상태 |
|---|---|---|
| **겹(Layers)** | 여러 번 맞아야 없어진다. 최대 8겹 이상 | ✅ `Blocker.layers` |
| **아이템 전용** | 일반 매치로는 안 부서지고 아이템만 통한다 | ✅ `powerUpOnly` |
| **색 지정** | 특정 색으로만 처리된다 | ✅ `color` |
| **숨김(Hidden)** | 다른 걸 치워야 드러난다 | ✅ 🔶 첫 타격은 드러내기만 |
| **바닥(Bottom)** | 아래로 떨어뜨려 판 밖으로 빼내야 한다 | ✅ `fallsOut` |
| **이동(Moving)** | 매 턴 스스로 움직인다 (로얄킹덤 골렘) | ✅ `golemHook` |
| **생성(Produce)** | 매 턴 무언가를 뱉어낸다 (우편함→편지) | ✅ `producerHook` |
| **보조(Helper)** | 플레이어를 돕는 요소 | ⬜ 종류가 다양해 개별 구현 |
| **하단 레이어** | 보석 **아래** 깔린다. 그 칸에서 보석이 터져야 벗겨진다 | ✅ `Cell.ground` |
| **벽(Wall)** | 칸이 아니라 **칸 경계**에 있다. 스왑·낙하를 막는다 | ✅ `Cell.walls` |
| **방패(Shield)** | 겹보다 먼저 벗겨야 하고 **폭발로만** 벗겨진다 | ✅ `shield` |
| **분열(Split)** | 부서지면 작은 것들로 쪼개진다 (거대 골렘) | ✅ `splitsInto` |
| **그릇(Container)** | 떨어져 들어온 보석을 **받아서 담는다** | ✅ `Cell.collector` |
| **투입구(Spawner)** | 그 열에 나오는 새 보석의 색을 고정한다 | ✅ `Cell.spawner` |
| **컨베이어** | 정해진 경로를 따라 매 턴 한 칸씩 민다 | ✅ `conveyorHook` |

> **6.4는 한 번 틀렸다가 화면에서 잡혔다.** 처음엔 "장애물이 열을 끊고, 끊긴
> 아래 구간은 새 보석을 못 받는다"로 뒀는데, 그러면 **그 칸이 영영 비어 있게 된다.**
> 실제로 판에 구멍이 뚫린 채로 남았고 골렘이 그 빈칸과 자리를 바꾸면서
> 구멍이 위로 올라오기까지 했다.
>
> 지금 중력은 "더 이상 움직일 게 없을 때까지" 반복한다:
> ① 바로 위에서 내려온다 ② 위가 막혔으면 대각선 위에서 끌어온다
> ③ 맨 윗줄이 비면 새 보석이 들어온다.
> **새 보석은 맨 윗줄로만 들어온다** - 장애물 아래에서 솟아나면 안 되기 때문이다.
>
> 화면에 넘기는 이동 정보는 중간 단계가 아니라 "처음 자리 → 끝난 자리"다.
> 중간 단계를 넘기면 한 턴에 같은 보석이 여러 번 움직이는 것으로 보인다.

> **6.7이 왜 중요한가**: 고정 장애물과 같이 취급하면 떨어뜨려 빼내야 할 상자가
> 제자리에 붙박여 레벨을 영영 못 깬다. 중력에서 "열을 끊는가"는
> `blocksFalling()`이 판단하고, `fallsOut`인 장애물은 보석과 똑같은 짐으로 다룬다.
>
> **6.9는 한 번 틀렸다가 고쳤다.** 처음엔 "아래가 비어 있을 때만 내려온다"로
> 뒀는데, 이 훅은 턴이 끝난 뒤 — 중력이 판을 이미 다 채워놓은 뒤 — 에 돌기 때문에
> **빈 칸이 존재하지 않아 골렘이 영영 못 움직였다.** 기능이 통째로 죽어 있었고
> 테스트는 전부 초록이었다(테스트가 인위적으로 칸을 비워놓고 확인했으므로).
> 화면에 올려서 6수를 둬보고서야 드러났다.
>
> 지금은 아래 보석과 자리를 맞바꾸며 내려온다. 판이 흔들리는 양이 보석 하나로
> 끝나서, 아래로 밀어붙여 줄줄이 올리는 방식보다 읽기 쉽다.
> 고정 장애물이나 구멍에 막히면 그 턴은 머문다.

> **6.2가 왜 중요한가**: 칸마다 세면 로켓 하나가 벽을 따라 지나갈 때 인접 칸이
> 여러 개 터지면서 8겹짜리 장애물이 한 방에 사라진다. 그래서 clear 단계마다
> 장애물당 한 겹으로 제한했다. 레퍼런스가 정말 그런지는 확인 필요.

#### 6.0.1 2차 조사로 추가한 축 (2026-08-25)

레퍼런스 도움말과 위키를 다시 훑어 나온 것들. 전부 **기존 축의 리스킨이 아니라
새 동작**이라 축을 늘렸다.

| 축 | 뜻 | 출처가 된 요소 | 상태 |
|---|---|---|---|
| **번짐(Spread)** | 부서지면 사라지는 게 아니라 **주변에 퍼진다** | 꿀단지(3x3 꿀), 화분(3x3 잎), 거북(제 열에 잎) | ✅ `Blocker.spreads` |
| **선행 조건(Requires)** | 판에 그 종류가 남아 있으면 **무적** | 묘비←유령, 색섞개←물감통, 성←금속탑 | ✅ `Blocker.requires` |
| **덩어리(Group)** | 여러 칸이 **하나의 장애물** | 마법의 벽, 돌뱀, 성 | ✅ `Blocker.group` |
| **약점(Weak)** | 덩어리에서 **한 칸으로만** 타격이 통하고, 그게 부서지면 전체가 무너진다 | 돌뱀의 머리 | ✅ `Blocker.weak` |
| **낙하물(Drops)** | 부서진 자리에 **아이템을 남긴다** | 전기상자→전기공 | ✅ `Blocker.drops` |
| **자폭(Explodes)** | 부서지며 **주변을 함께 터뜨린다** | 통, 폭죽탑 | ✅ `Blocker.explodes` |
| **이동 방식(MoveKind)** | 아래로만이 아니다 — 순간이동·왕복·경로 | 거대 드릴, 물탑, 돌뱀·눈사람 | ✅ `Blocker.move` |
| **주기(EveryN)** | 매 턴이 아니라 **N턴에 한 번** 뱉는다 | 허수아비(4턴) | ✅ `Blocker.everyN` |
| **가림(Hides)** | 아래에 무엇이 있는지 **안 보인다** | 구름 | ✅ `Cover.hides` |
| **재생(Regrow)** | 이번 턴에 하나도 못 없앴으면 **되살아난다** | 버섯(흙 위에) | ✅ `regrowHook` |
| **넓힘(Grow)** | 바닥이 **벗겨지는 게 아니라 옆으로 번진다** | 젤리 | ✅ `Ground.spreads` |
| **붙잡음(Locks)** | 덮인 보석을 **못 옮긴다.** 중력도 안 통한다 | 사슬, 꿀 | ✅ `Cover.locks` |
| **덮개 아이템 전용** | 일반 매치로는 **한 겹도 안 깎인다** | 사슬 | ✅ 🔶 `Cover.powerUpOnly` |

> **`requires` 하나로 두 가지를 덮는다.** "앞을 치워야 뒤가 열린다"(묘비←유령)와
> "누가 지켜주고 있다"(크리스탈·호위병이 지키는 대상)는 방향만 반대일 뿐
> **다른 칸의 생사가 이 칸의 무적을 결정한다**로 같다. 축을 둘로 나눴다면
> 같은 코드를 두 벌 갖게 됐을 것이다.

> **`spreads`가 골렘의 특수 처리를 흡수했다.** 원래 "골렘이 바닥에 닿으면 잔해를
> 쏟는다"는 훅 안에 박아 넣은 한 번짜리 코드였다. 거북이 "바닥에 닿으면 제 열에
> 잎을 깐다"로 같은 모양이라는 걸 발견하고 축으로 올렸다 — 이제 퍼지는 모양
> (`area`/`column`)만 데이터로 다르다.

> **붙잡음 축은 실제로 어긋나 있던 걸 고친 것이다.** 사슬 설명은 "보석을 붙잡는다"
> 였는데 `isSwappable`은 덮개를 보지 않아서 **사슬 낀 보석이 자유롭게 움직였다.**
> 반대로 화면은 덮개가 있으면 무조건 못 집게 막아서, 얼음 낀 보석은 엔진이
> 허용하는데도 못 옮겼다. 지금은 양쪽 다 `isCellSwappable` 하나를 본다.

> **6.40은 "요소처럼 보이지만 요소가 아닌 것"의 첫 사례다.** 레퍼런스 위키가
> 보물지도를 상단 레이어로 분류해 놔서 덮개로 넣어뒀는데, 설명을 읽어보니
> 판에 놓이는 건 **병**이고 지도는 그 병들의 진행 표시였다. 카탈로그에는
> 병만 두고, 지도는 레벨 목표(`blocker: bottle`)로 표현한다.
>
> 분류표를 그대로 축으로 옮기면 이런 게 섞여 들어온다. **분류는 그림의 분류이지
> 동작의 분류가 아니다.**

> **6.36을 안 지키면 사슬의 뜻이 무너진다.** "옮길 수 없다"만 구현하고 중력을
> 빼놨더니, 아래가 비는 순간 **보석만 빠져나가고 사슬은 그 자리에 남아
> 다음에 내려온 엉뚱한 보석을 붙잡았다.** 붙잡는다는 말의 뜻이 아니다.
>
> 얼음과 갈리는 지점이기도 하다 — 얼음 낀 보석은 옮길 수도 떨어질 수도 있다.

> **6.37은 6.36을 넣자마자 생긴 구멍을 메운 것이다.** 중력 루프에 "위가 받을 수
> 있는 칸이면 기다린다"가 있었는데, 붙잡힌 보석이 든 칸은 받을 수는 있지만
> **내려오지 않는다.** 기다리면 아래가 영영 빈다. "받을 수 있는가"가 아니라
> "비어 있는가"로 봐야 했다.

> **젤리는 목표의 부호가 반대인 첫 요소다.** 다른 모든 목표는 "판에 남은 것을
> 줄인다"인데 젤리는 "판을 채운다"다. `countOnBoard`도 프로펠러 조준 점수도
> 젤리에서만 조건이 뒤집힌다 — 목표 종류를 `ground`와 따로 `spread`로 나눈 이유다.
> 한 종류로 뭉쳤다면 세는 방향을 요소별로 분기해야 했을 것이다.

> **6.34가 없으면 한 수에 판이 다 덮인다.** 번진 칸을 다시 씨앗으로 삼으면
> 연쇄적으로 퍼져서 레벨이 한 수에 끝난다. 판정을 **원본 보드**에서 읽는다.

> **6.32가 없으면 레벨이 안 끝난다.** 목표를 채운 순간 하나가 다시 자라서
> 영원히 남는다. 재생은 "덜 치웠을 때의 벌"이지 "끝나지 않게 하는 장치"가 아니다.

> **재생 축 때문에 훅이 턴의 결과를 볼 수 있어야 했다.** 그전까지 훅에 넘어가는 건
> 턴이 끝난 뒤의 보드 하나뿐이라 "이번에 버섯이 깎였는지"를 알 방법이 없었다.
> `TurnContext`로 그 턴의 피해 기록을 함께 넘긴다 — 보드만으로는 표현할 수 없는
> 첫 번째 규칙이었다.

> **버섯은 처음에 잘못 넣었던 것을 고친 사례다.** 이름만 보고 "잔디 같은 하단
> 레이어"로 추정해 `verified: false`로 뒀는데, 실제로는 **흙 위에 자란 장애물**이고
> 재생까지 있었다. 추정 표시가 실제로 값을 한 지점이다.

> **6.27을 왜 이렇게 정했나**: 폭발이 또 폭발을 부르는 경우를 `applyDamage` 안에서
> 재귀로 풀면, 몇 겹이든 **한 화면에 뭉쳐 나와서** 무엇 때문에 터졌는지 볼 수 없다.
> 씨앗으로 넘기면 연쇄 단계가 하나씩 늘어 화면에 순서대로 재생된다.

> **"이동" 축이 구조적으로 제일 무겁다.** 턴이 끝난 뒤 보드가 스스로 바뀌어야
> 하는데, 그 자리는 `resolveTurn`의 `onTurnEnd` 훅과 `board-effect` 단계로
> 이미 뚫어뒀다. 골렘 자체의 동작만 채우면 된다.

| 6.22 | 투입구는 **한 열에 수집물 하나씩만** 흘려보낸다 | ✅ 🔶 |
| 6.23 | 컨베이어는 경로를 순환한다 — 보석이 사라지거나 생기지 않는다 | ✅ 🔶 |
| 6.24 | **수집물은 폭발·부스터에 면역이다** — 오직 중력으로만 움직인다 | ✅ 🔶 |

> **6.24를 왜 이렇게 정했나**: 처음엔 폭발이 수집물을 없앴다. 그러면 애써 흘려보내던
> 것이 사라져 진행이 날아가고, 수집물 수가 한정된 레벨은 **아예 못 깨게 된다.**
> 지금은 폭발이 수집물 위를 지나가고 아래 보석만 치운다 — 없애는 게 아니라
> **길을 내주는** 셈이라 로켓이 오히려 유용해진다.
>
> 레퍼런스가 "폭발이 수집물을 대신 담아준다"일 가능성도 있다. 확인 필요.

> **여기서 규칙 충돌을 하나 만들었다가 고쳤다.**
>
> 처음엔 "그릇이 특정 색 보석을 받는다"로 만들었다. 그러자 한 색만 내보내는
> 투입구가 그 열을 같은 색으로 채웠고, **같은 색 셋이 세로로 서는 순간 그게 곧
> 매치**라서 터지고 또 같은 색이 내려오며 **연쇄가 끝나지 않았다.**
> 한 턴에 50연쇄(상한)까지 돌면서 보석이 무한히 떨어졌다.
>
> 색 보석을 담게 하는 한 이 충돌은 피할 수 없다. 그래서 **매치되지 않는
> 수집물**을 별도로 뒀다 — 레퍼런스에서 선반에 담기는 게 보석이 아니라
> 트로피·편지인 이유가 이것이다. 규칙 두 개가 부딪히면 대개 모델이 틀린 것이다.
>
> 수집물은 스스로 없어지지 않으므로 계속 쏟으면 열이 짐으로 막힌다.
> 그래서 한 열에 하나씩만 흘려보낸다. 아래 보석을 치워 길을 내주는 게
> 이 레벨의 퍼즐이다.

### 아직 없는 것

커튼, 다이너마이트, 드릴, 슬롯머신, 자석, 블라인드, 용광로, 고대금고.
대부분 위 축의 조합이거나 개별 연출이라 필요할 때 추가하면 된다.

| 7.1 | **목표 달성형이지 점수형이 아니다** | ✅ | 기존 `royal-match`는 점수 목표라 성격이 다르다 |

| 7.3 | **한 레벨에 목표가 여럿일 수 있다** | ✅ | 전부 만족해야 한다 |
| 7.4 | 제한된 이동 횟수 안에 전부 달성해야 클리어 | ✅ | |
| 7.5 | **목표를 채우는 순간 이긴다 — 수가 남아 있어도** | ✅ | 판정 순서가 반대면 마지막 수로 채운 판이 패배가 된다 |
| 7.6 | 무효한 수는 이동 횟수를 소모하지 않는다 | ✅ | |
| 7.7 | 클리어 시 남은 수를 아이템으로 바꿔 터뜨리는 연출 | 🔶 | 흔한 관례 |
| 7.8 | 레벨 포맷 | ✅ | 배치는 **테스트 픽스처와 같은 표기**를 쓴다 |

> **레벨 배치를 테스트 표기법으로 적는 이유**: 레벨을 그대로 테스트에
> 붙여넣을 수 있어야 한다. 표기가 갈리면 "레벨에서만 재현되는 버그"가 생긴다.
> 실제로 레벨 4를 적을 때 `#2.`를 붙여 써서 열 수가 어긋났는데, 파서가
> "3번 행의 칸 수가 6개다"라고 바로 잡아줬다.

### 7.9 난이도 — 봇으로 자동 측정 ✅

| 항목 | 값 | 출처 |
|---|---|---|
| 로얄매치 하드 레벨 비율 | **10레벨당 2개** | 📖 |
| 로얄킹덤 하드 레벨 비율 | **10레벨당 4개** | 📖 |
| 난이도 사이클 | **5~10레벨 주기**, 각 사이클 첫 레벨은 쉽게 | 📖 |
| 난이도 지표 | 클리어까지 걸린 시도 횟수. 쉬움 1~3회, 어려움 20~35회 | 📖 |

`measureDifficulty(level, runs)` 가 승률 / 평균 사용 수 / 시도당 클리어를 낸다.

**봇이 못 하는 메커니즘도 있다.** 그릇 레벨은 "수집물 아래를 비워 길을 내주는"
판인데, 아무 데나 많이 터뜨리는 봇은 이걸 못 해서 승률 0%가 나왔다.
봇에 "수집물 아래를 치우면 가산점"을 넣자 0% → 38%가 됐다.
**승률이 낮을 때 "레벨이 어렵다"인지 "봇이 못 한다"인지 먼저 갈라야 한다.**

**주의: 봇 숫자를 사람 난이도로 그대로 읽으면 안 된다.** 봇은 매 수마다
모든 후보를 훑어 당장 가장 많이 터지는 수를 고르므로 사람보다 잘 둔다.
봇 승률 80%가 사람 승률 80%를 뜻하지 않는다. 봇 측정이 확실히 잡아주는 것은:

- **회귀** — 규칙을 바꿨을 때 난이도가 흔들렸는지 (예: TNT 반경을 올리면 승률이 뛴다)
- **상대 난이도** — 레벨끼리의 순서
- **달성 불가능한 레벨** — 승률 0%면 목표치나 배치가 잘못된 것

사람 기준 절대 난이도는 결국 사람이 플레이해서 보정해야 한다.

현재 레벨(봇 200판, greedy):

| 레벨 | 수 | 승률 | 평균 사용 수 |
|---|---|---|---|
| 1 | 20 | 78% | 15.1 |
| 2 | 15 | 85% | 8.1 |
| 3 | 26 | 73% | 16.4 |
| 4 | 6 | 96% | 3.3 |

> **3.11(아이템이 줄을 끊는다)로 바꾸자 레벨 1 승률이 75% → 35%로 떨어졌다.**
> 아이템이 판에 남아 매치를 방해하기 때문이다. 이동 횟수를 전부 다시 잡았다.
> 규칙 하나가 난이도 전체를 흔든다는 사례.

> 이 숫자는 **봇의 실력에 의존한다.** 4번 작업에서 봇의 수 선택을
> "연쇄까지 시뮬레이션"에서 "즉시 매치 크기"로 바꾸자 레벨 1 승률이
> 96% → 48%로 떨어졌고, 이동 횟수를 다시 조정해야 했다.
> 봇을 손대면 모든 레벨의 숫자가 같이 움직인다는 뜻이므로,
> **봇 변경과 레벨 튜닝을 같은 커밋에 섞지 말 것.**

## 13. 레벨 생성

**내용은 고르고, 난이도는 잰다.**

무엇을 놓을지는 진행표가 정하고, 그게 얼마나 어려운지는 아무도 계산하지 않는다 —
봇에게 30판씩 시켜서 **승률로 확인**한 뒤 **이동 횟수만 조절해** 목표에 맞춘다.

| 파일 | 역할 |
|---|---|
| `engine/generate.ts` | 배치·목표 만들기, 이동 수 이분 탐색 |
| `data/schedule.ts` | 몇 번째 판에서 무엇이 처음 나오나, 목표 승률 곡선 |
| `scripts/bake-jewel-levels.sh` | 한 판씩 구워 JSON에 넣기 |
| `data/generated-levels.json` | 구운 결과. 사람이 열어보고 고쳐도 된다 |

| # | 규칙 | 상태 |
|---|---|---|
| 13.1 | 목표는 **배치에서 뽑는다** — 판에 없는 걸 목표로 걸지 않는다 | ✅ |
| 13.2 | 이동 수는 목표 승률에 닿는 **가장 적은** 값 | ✅ |
| 13.3 | 어떤 이동 수로도 목표에 못 닿으면 **배치를 새로 흔들어** 다시 만든다 | ✅ |
| 13.4 | 한 판에 **새 요소는 하나만** | ✅ |
| 13.5 | **확인된 요소만** 쓴다 (`verified: true`) | ✅ |
| 13.6 | 다섯 판마다 쉬어가는 판 — 재료도 가볍게 | ✅ |
| 13.7 | 움직이는 것(골렘)은 목표로 걸지 않는다 | ✅ |

> **13.2가 없으면 늘 최대치가 답이 된다.** 이동 수를 늘리면 승률은 언제나
> 올라가므로 "목표를 넘기는 값"을 아무거나 고르면 45수 판만 나온다.

> **13.7의 이유**: 골렘은 바닥에 닿으면 스스로 사라지는데 그건 부순 게 아니라
> **당한 것**이라 목표로 세지 않는다. 그래서 "골렘 제거"를 걸면 제때 못 부순
> 판이 영영 못 깨는 판이 된다 — 16·21·26레벨이 실제로 그렇게 막혔다.

> **뒤로 갈수록 재료가 늘어야 한다.** 목표 승률만 낮추면 생성기는
> **이동 수를 줄여서** 그 승률을 맞춘다. 할 일이 적은 판을 수만 조인 꼴이라
> 판이 짧고 운에 좌우된다 — 처음 구웠을 때 후반이 4~5수짜리로 쪼그라들었다.
> 어려워지는 방향은 "수를 조이는 것"이 아니라 **"할 일이 느는 것"**이어야 한다.

> **한 판에 한 프로세스.** 한 프로세스에서 수십 판을 이어 구우면 node가
> 세그폴트로 죽는다(원인 미상, 다른 작업이 같이 돌 때 특히 잘 난다).
> 판마다 새로 띄우면 그 문제가 없고, 중간에 죽어도 이미 구운 판은 JSON에 남는다.
